# project-language

Runnable capabilities for the book *Language: When Intelligence Enters the Channel* (manuscript and planning live in [`ernanhughes/language`](https://github.com/ernanhughes/language)).

The idea is that the book's claims should be something you can run. This repository collects the capabilities explored in the earlier `opencode-*` plugin projects into one project, built so the host is replaceable.

## Quick start

Windows or any system with Node 25. No model and no API key are needed.

```text
npm ci               install the pinned dependencies
npm run verify       typecheck and the full test suite
npm run examples     run every example (Part I and Part II) and report which ran
npm run test:postgres  run the live-Postgres tests that are skipped by default
```

`npm run test:postgres` uses the local development database `postgresql://language:language@localhost:5432/language` unless `MEMORY_BASELINE_DSN` is set, and needs the `vector` and `pg_trgm` extensions. Individual examples are `npm run example:ch07` to `example:ch12`, `example:admission` and `example:radar`. `PART-TWO-CONTRACT.md` explains the Part II code.

## Shape

```text
core/       host-independent libraries; import nothing from any agent host
host-pi/    thin Pi adapter; the only place that imports Pi
harness/    a real Pi session driven by a faux model, for tests
```

The rule that keeps the host incidental: `core/` never imports Pi (or OpenCode). `host-pi/` is the only file set that does. Swapping the host means rewriting `host-pi/`, not the capabilities.

The host supplies model access and the request path. These modules work on what flows through, at the host's documented extension points, and never alter the host.

## Status

| Piece | State |
|---|---|
| `core/authority` + `host-pi/authority.ts` | **Walking skeleton.** A Pi `tool_call` is turned into a proposal, evaluated against a policy, and blocked, approved or allowed. Run through a real Pi session with a faux model. |
| `core/language` + `host-pi/language.ts` + `examples/conversation-state` | **Adapter built and tested in a real Pi session. Not Chapter 7's record.** Keeps a *conversation's* communication state (decisions, constraints, definitions, ambiguities) in a Git-backed store, and `before_agent_start` hands the model the rendered projection once per turn, read-only. Unverified state (torn, corrupt, unaccepted human edit, missing thread) is never injected; the turn proceeds without it and the outcome is recorded as a session entry. It was first labelled Chapter 7 by mistake; Chapter 7 describes a record of a *document*, which is `core/record`. This belongs with the later parts of the book (personal and conversational state). Run `npm run example:conversation-state`. |
| `core/record` + `host-pi/record.ts` + `examples/ch07-record` | **Chapter 7's record, tested in a real Pi session.** A semantic record of a *document*: claims, directed relations (including exceptions, causes, and associations the source rejects), qualifiers, sequence, evidence status and spans. `validateRecord` checks, for any record and not just the fixtures, that it is for this source, that every entry cites a non-empty passage the source contains, that no entry carries a field outside the schema (so no reader or rendering information can ride along), that relations and qualifiers point at things that exist, and that a qualifier's condition and gap lie inside its cited passage. Renderings (diagram, table, timeline) are drawn from it; every line of the diagram and timeline and every table row names its record entry; conditions attached to a claim appear whether or not the claim is also the end of a relation. Any entry walks back to its passage and offsets. It stores what the source says, including what the source leaves unsupported ("none cited"), not a corrected fact. The model can ask for a view or a location and has no tool that writes the record; the host will not render a record that fails validation. Run `npm run example:ch07`. **Shows the mechanism only.** The chapter's prediction (renderings through a record agree more, contradict less and trace back further than direct ones) is an empirical bet this does not test: the "direct" renderings are constructed, agreement is by construction, the agreement check is phrase presence, and the record is written by hand. **Limits:** a repeated quotation resolves to its first occurrence; nothing checks that a label means what its passage means; there is no concepts field, extraction or revision log. |
| `core/sidecar` + `host-pi/sidecar.ts` + `examples/ch08-sidecar` | **New module, tested in a real Pi session** (Chapter 8). No lifted provider covers it. Layers are kept apart and an item's layer is fixed by the door it came through (the model can only reach `sidecar_propose`, which always yields a model-answer candidate). A derived item's content **is** its verbatim quotation, re-checked against the source's hash; the system's reading of it travels separately as a labelled gloss, so an unsupported claim cannot be given the derived label by being written into the content. An anchor whose source cannot be consulted fails. Retrieved items must match their pinned excerpt. Stored objects of the wrong shape are reported as malformed. A model answer must state specific limits: `None.` and its relatives, stubs, sentences with nothing limiting in them, and the same limit pasted onto a second answer are refused, and so is a `drew_on` reference to something that does not exist. The margin is capped, so it cannot be flooded. Nothing notifies, and nothing is added to the system prompt (the model's own tool calls still contain what it wrote). The ledger has two columns and no total. Run `npm run example:ch08`. **Known weaknesses:** the limits rule checks specificity, not honesty (`This answer may be fully trusted without any checking at all.` passes, pinned); the item id shows integrity, not authorship; the ledger counts events it is given and the adapter emits only shown, used and dismissed. |
| `core/relations` + `host-pi/relations.ts` + `examples/ch09-relations` | **New module on top of `core/relate`, tested in a real Pi session** (Chapter 9). Similarity finds candidates and carries no label; a relation step labels them; whether to show a label depends on the reader's task. Every record says how it arose (asserted by a source / classified / adjudicated) and how far to trust it. A classifier's output is only ever a proposal. Only a person adjudicates, and **a person's adjudication is not displaced by a later classification of the same pair**: the rule is in the core, and the host refuses and does not record a model's relabel. A contradiction without a declared, shared scope is flagged and not shown as one; confirming a label does not confirm a scope unless the person says so (`scope-confirmed`), and the person can supply a direction (`dir=`). "Adds nothing" is not a relation: it is measured as novelty against the text being read, so a near-duplicate is held back, and it is never applied to a contradiction, update or implementation. Run `npm run example:ch09`. **Known limits:** the classifier (`core/relate`, cue-based) gets 5 of 7 hand-picked probe pairs; it reads the scope-condition example as a contradiction (the record's scope flag catches that, the label stays wrong) and misses a contradiction with no negation word. An explicit-revision cue was added after seeing that miss, so the probe is no longer independent of it; an 8-pair regression set guards it, and `no longer accepts` reads as a contradiction. Novelty is measured against the text being read, not the reader's wider knowledge, over invented snippets. The scope guard is string equality and needs scopes declared by someone. The core's `adjudicate` trusts the caller's `human`; the host command is the boundary, not authentication. |
| `core/preservation` + `host-pi/preservation.ts` + `examples/ch10-preservation` | **New module composing `core/evidence` and `core/verify`, tested in a real Pi session** (Chapter 10). The transformation is observed as evidence; each obligation declared beforehand is a verify criterion over it (lost / survived / not assessable, three-valued); a profile by dimension with no total; function (can the task still be done, and sooner or later than in the source) apart from content, as a proxy; candidate additions flagged for review. The instrument is probed by breaking a faithful output: drop its sentence, reverse a relation, turn a hedge into a certainty, change the first number, and shred a sentence into a bag of its own words (keyword-stuffing). An obligation can be anchored to a key phrase whose word order must survive within a sentence; an obligation no probe can be applied to keeps the check unvalidated. **An instrument's standing cannot be asserted:** a bare `validated` is not believed, and a validation counts only for the obligations whose probes were run (compared by a hash of the obligations, not the timestamp). Unparseable times are refused. Run `npm run example:ch10`. **Findings:** `core/lens`'s preservation report originally missed a reversed relation and a hedge turned into a certainty; the probe caught it and the report was made order-, negation- and hedge-aware. **Known limits:** that report still cannot see one word swapped for its opposite inside a long sentence and reads a faithful paraphrase as lost; copying the key phrases in order around nonsense passes anchored obligations (pinned); pattern obligations are source-independent and can accept a negated claim; emphasis and the truth of the source are not covered; the addition check is a heuristic for numbers and absolute words. |
| `core/ladder` + `host-pi/ladder.ts` + `examples/ch11-ladder` | **New module, tested in a real Pi session** (Chapter 11). Only the enforceable part of the chapter is built: a word's reading is a declared decision bound by hash to the words that prompted it (the passage hash is recomputed at use, so editing the passage invalidates earlier settlements); a check on an unsettled reading is INCONCLUSIVE and never a pass; a model may propose a reading but only a person settles it, and **a later proposal never unseats a settled or deferred decision**; only a person can say the more explicit version still means what they meant, and **that answer is tied to the reading it was given for** (if the reading changes it is reported as unasked and stale); a translation with an open choice cannot claim to have narrowed anything; a probe asks whether a selector follows an option's name or its definition, and a selector that never returns a valid option is not called stable. The chapter's job-queue story runs: "completed job" passes flawlessly while J1 is charged twice, and "external effect" fails. The retry limit counts retries (an attempt after the first), not attempts. Run `npm run example:ch11`. **Not built, and not claimed:** any ranking of the rungs, the six-axis comparison, and the reported finding about option names (the probe is run only on a deliberately defective simulated selector, so it shows the probe works, not what any real model does). Translation relations are caller-supplied, and a person can rubber-stamp the wrong meaning. Whether people find the mediation worth the labour is the chapter's own open question and is untested. |
| `core/browser` + `host-pi/browser.ts` + `examples/ch12-browser` | **Composition of the Part I pieces, tested in a real Pi session** (Chapter 12). A document record (via `core/record`); a representation chosen by task, where leaving the source unchanged is an output; deterministic renderings plus a model's, all through one gate; a margin built from `core/sidecar` and `core/relations`. The record is validated before anything built from it is delivered; if it fails, every view falls back to the source. The gate checks each view separately, validates its own check first (an unvalidated check cannot authorise anything), repairs while attempts remain, and otherwise ships the source. Its obligations require the condition's actual words and the gap interval (not cue words), each hypothesis's evidence on its own row, and each arrow's direction; the check is probed by altering a value, removing evidence and reversing an arrow. **A view is closed once accepted or handed back to the source**: later submissions are refused and not recorded, and only the reader reopens a task (`/browser reset`). Annotations carry only a condition and gap that lie inside the cited passage. `/browser show look_up_fact <query>` says where the passage is. Run `npm run example:ch12`. **Findings:** a check over a diagram and table together cannot see one row lose its condition; shredding each view showed some obligations were weak; a cross-review then found four more holes (condition value, evidence, lifecycle, record validation), all now tests. **Not shown:** any comparison with the plain page (the stages cost time; no benefit is claimed); that a model can build a record that passes validation (it is written by hand); source access alongside every accepted view; an interactive margin; a producer that copies the right phrases in order around something else, or a shift in emphasis; control over arbitrary assistant messages (the gate governs the views `/browser` shows). |
| `core/radar/src/attention` + `host-pi/radar.ts` + `examples/part-two-radar` | **Part II, human-side path, first bounded pass.** The Radar's decision split into independent axes (qualification, unit selection through `core/compiler`, resolution, delivery, observation) with a versioned delivery lifecycle (`PENDING`/`DELIVERED`/`WITHDRAWN`/`EXPIRED`; re-evaluation appends a revision and never edits one). Enforced over one invented afternoon: a subscription is matched as written; a relation needs a scope-preserving bridge; membership, nesting and closure are reported apart from wording; timing cannot change resolution; `QUEUE`+`BRIEF` and `DIGEST` are reachable; reopening re-runs every gate on the current candidate; a rendering uses only compiler-selected units and an undecomposed item is not summarised; a model-delivery receipt and a human-presentation receipt cannot stand in for each other, and noticing, use and benefit stay `unknown`. Contract: [`PART-TWO-CONTRACT.md`](PART-TWO-CONTRACT.md). Run `npm run example:radar`. **Limits:** scripted model; the bridge and the units are supplied, so nothing here discovers a relation; the wording check is anchored phrases and content words and is defeated by copying the right words around a different meaning; the timing table is a declared policy, not a measured one; the lifted `decide` is unchanged and still folds the axes together (pinned by a test). |
| `core/radar/src/attention` (`transcript`, `relevance`, `knowledge`) + `examples/part-two-talk` | **Chapters 14 to 16, without a host or a model.** A transcript in the youtube-transcript format becomes a hash-pinned source; units are exact spans (one can join minute 4 and minute 53) proposed by a stand-in for a model, which can suggest structure and cannot supply content. Relevance judgements belong to one purpose, carry a reason and a citation, and a unit judged not relevant still travels with the unit that depends on it. A graded knowledge state is derived from dated evidence, treats exposure as no evidence, and treats a familiar term in a different sense as unknown; omission needs known AND not needed. Run `npm run example:talk`. **Limits:** the proposals, judgements and the knowledge state are written by hand; nothing finds units, decides relevance or extracts concepts; no video, audio or slides; nothing persists. |
| `tmy/` | **Too Much YouTube, as a sub-project.** A filter over your subscriptions: reads each channel's public feed, screens what is new against your declared purpose and terms, and writes a daily digest of what to look at, what is available, what was not shown and why, and what the scan could not see. A ledger stops anything being shown twice and re-screens withheld videos when your interest changes. Replaces the older Python `tmy`, keeping its concepts (channel list, latest videos, timestamped transcripts, "what I am working on") and dropping similarity-as-relevance. Run `npm run example:tmy` (invented feeds) or see `tmy/README.md`. **Limits:** decides from titles and descriptions only; reads no transcripts yet; no model judge, no Postgres, no schedule; nothing measures whether it saves time. |
| Other `core/*` modules (compiler, lens, relate, radar, evidence, verify, proof, work, vfs, language, transport, remembering) | **Lifted, not yet qualified.** Copied from the earlier plugin repos minus their OpenCode-SDK files; see `PROVENANCE.md`. Typecheck is clean and their own tests pass (see `PROVENANCE.md` for the 3 skips and the retired packaging tests). None has been exercised against Pi yet; passing their own tests says nothing about behaviour inside a Pi session. |
| `opencode-expertise`, `opencode-observability` | **Not lifted.** They have no TypeScript `src/` of the same shape (CLI/library and Python harness). Decide separately. |

Today the only rendering `core/language` produces is the record itself, wrapped in a notice and delimiters. It shows the source / record / rendering distinction, but not yet one record rendered several ways; that needs `core/lens`.

A faux-model test shows that the gate fires and blocks. It says nothing about real-model behaviour.

Part I was cross-reviewed by a second AI at commit `3239630`; every finding, and what became of it (fixed with a test, left as a stated limit, or not built), is in [`REVIEW-RESPONSE.md`](REVIEW-RESPONSE.md). The same author wrote the code and fixed the findings, so the fixes are not independent validation.

## Run

Pinned to Pi 1.0.4 (the release *Pi Agents* is written against). The lockfile is taken from `pi-agents/examples` so transitive packages match; a fresh unpinned install pulls a newer `pi-codemode` that does not load.

```bash
npm ci
npm run verify   # typecheck, then tests
```

Developed and run on Node 25.8. The Pi release this targets states Node 22.19 or later; this project has not been run on 22. TypeScript runs by Node's type stripping, with `--experimental-transform-types` for the lifted code.
